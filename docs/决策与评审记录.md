## 一、V0.1 设计文档评审

> **2026-09-30 更新**：本节列出的 3 个 critical 缺陷**已全部修复并落进代码**，
> 且各有单测兜底（`tests/test_engine.py`）。原文保留，用于记录设计来龙去脉。

**总体判断**：骨架方向正确，V0.1 边界守得好（不绑模型、不内置业务逻辑、不做分支并行）。
但有 3 个缺陷必须补，否则一跑就踩坑。

### Critical（必须先补）

1. **`unload()` 必须放进 `finally`**
   当前流程 load → infer → unload，`infer` 一旦抛异常，`unload` 永不执行 → 显存泄漏。
   在"单 GPU 显存受限"这个核心场景下是硬伤：一次失败，后续全部节点都会挂。

2. **`params` 没有传递通道**
   YAML 里声明了 `params: {}` 并注明"会传入插件"，但接口是 `infer(workflow_data)` / `run(workflow_data)`，
   签名里根本没有 params。这两处自相矛盾。
   解法二选一：把 params 注入 `workflow_data`（如 `meta["node_params"]`），或接口改为 `infer(workflow_data, params)`。

3. **KB 插件的定位含糊**
   KB 被列为三类插件之一，但 YAML 的 `type` 只支持 `llm / skill`，
   KB 只能以 `kb_plugin_name` 形式挂在 LLM 节点上。
   必须二选一：明确"KB 只是 LLM 节点的检索资源、不参与调度"，或支持 `type: kb` 成为独立节点。

### 次要建议

4. `node_id.xxx` 前缀从"建议"升级为**框架强制**：框架层 diff payload，非本节点前缀的新增/覆盖即告警或报错。
5. **失败策略未定义**：建议 V0.1 明确 fail-fast + 记入 trace。
6. **插件发现约定未写明**：`plugins/<name>/plugin.py` 怎么定位插件类、一个文件多类怎么办、
   导入失败是否跳过、以及 `from plugin_base import ...` 依赖根目录在 `sys.path` 的问题。
7. 串行 + 每节点 load/unload，多 LLM 节点会反复加载权重 → 预留 `keep_alive` / 同插件复用开关。
8. `meta["trace"]` 建议结构化（时间 / node_id / level），不要只塞字符串。
9. 显存回收由框架统一 `gc.collect() + torch.cuda.empty_cache()`，不要指望每个插件自己写。

## 二、与既有项目的融合分析（关键）

**用户洞察**：V0.1 框架 与 既有项目计划（文生视频四阶段 / 短剧六步 / drama-app）**各自都没大问题，
真正的难点在两者的融合**。以下为拆解出的 5 条摩擦：

| # | 摩擦 | 说明 |
|---|---|---|
| 1 | **粒度差** | 老项目里"一步"（如分镜生成，内含并发/重试/落盘）比框架的"一个节点"粗——老的一步其实是**子流程** |
| 2 | **控制流差** | 框架只线性向前；老项目需要**回退修改**（单镜头重生成）+ **人机逐步确认** |
| 3 | **形态差** | 框架是内存态脚本；老项目是持久工程态（`project_dir` / `outputs` / `config` / 断点续跑） |
| 4 | **资产差** | 老项目产物是 MP4/图/音频/素材库（量大）；框架 payload 是 dict → 必须约定 payload 只放引用 |
| 5 | **并发差** | 框架串行；素片生成需并发 3 → 需要"节点内并发" |

**结论**：融合层 = 框架必须再长出的第二层骨头。
单流程不值得做；**多流程共用插件（标签剖析 / 分镜）**才值得。

## 三、框架验收清单（自用版）

用户定方向：**先完善框架，再让既有项目计划适应框架**。
因此"完善"的标准必须由老项目定义——做到能支持以下能力，才算完善好了。

| 老项目的需求 | 框架必须具备的能力 |
|---|---|
| 单镜头重生成 | 定点回退 + 重跑已完成节点 |
| 素片并发 3 | 节点内并发 |
| 断点续跑 / 工程目录 | checkpoint 持久化（每节点落盘）+ 恢复执行 |
| 分镜确认后再生成 | 人机暂停/继续（或外部驱动分段执行） |
| "分镜生成"内含并发+落盘 | 子流程 / 嵌套节点 |
| UI 要实时看进度 | headless API + 进度/日志回传 |
| MP4 / 图 / 音频等大件 | payload 只放引用 + 资产落盘目录约定 |
| 4GB 显存、v1 云端 API 为主 | 新增 `api` 插件类型（远程调用，load/unload 为空操作） |

**2026-09-30 进度**：

| 验收能力 | 状态 |
|---|---|
| checkpoint 持久化 + 恢复执行 | ✅ `core/checkpoint.py`（每节点落盘） |
| 人机暂停/继续（外部驱动分段） | ✅ `--stop-at` + `--resume`（`--from-node` 可定点重跑） |
| 节点内并发（素片并发 3） | ✅ `core/concurrency.py` |
| payload 只放引用 + 资产落盘 | ✅ `core/assets.py` |
| `api` 插件类型（远程调用） | ✅ `BaseAPIPlugin` |
| 子流程 / 嵌套节点 | ⏳ 待做 |
| headless API + 进度回传 | ⏳ 待做（已有 `on_event` 回调基础） |

**提醒**：目标是"刚好接住这几条流程"，**不是做通用框架**。
一旦追求通用，就会长出配置地狱（开关、表达式、条件语法），丢掉"纯骨架、无业务"的克制。

## 四、GitHub 竞品调研

**结论：类似的很多，但本框架的精确组合确实少见。**

### 编排层（YAML / DAG 工作流）——不管显存
| 项目 | 相似点 | 缺口 |
|---|---|---|
| **Talos** (talos_cli) | YAML-first LLM DAG、轻量、插件 agents、CLI 类 Docker。**与设计最像**，动机同为"LangChain fatigue" | 不管模型显存生命周期 |
| **liman** | YAML 声明式节点（LLM/Tool/Function）+ 边条件 DSL | 早期项目 |
| **kdeps** | YAML DAG + 本地模型（Ollama/llamafile/GGUF） | Go 实现，扩展需会 Go |
| **Animus CLI** | 微内核 + 插件 + YAML workflow + 守护进程 | Rust，偏多代理编码 |
| LangGraph / Haystack / Dify | 成熟全面 | 重，且不管显存 |

### 显存 / 模型生命周期——不管工作流节点
- **LLM-Node**（本土，无头纯后端）：请求触发冷启动 / 空闲自动回收 / **显存不足动态驱逐**，YAML 配置。
  语义几乎就是 `load/unload`，但更聪明（按需 + 驱逐，而非每节点硬卸）。**值得直接借鉴**。
- Ollama（`keep_alive`）、Xinference、LM Studio、ComfyUI（节点 + 显存管理 + 插件生态）。

### 融合层——别人已做全（无独创性，可直接抄设计）
- **LightAgent 的 LightFlow**：checkpoint、resume/rerun、**approval nodes**、retries、DAG 依赖、
  step 输出传递、trace。**本框架要补的骨头它几乎全有。**
- **LangGraph**：checkpoint + `interrupt`（人机）+ subgraph（子流程）。

### 差异化判断
- 真实存在的窄切口：**进程内、节点级、框架强制的模型显存生命周期 + 极简骨架**。
  编排派不管显存，显存派不管工作流节点——接缝处确实空着。
- 但**融合层没有独创性**，已被 LightAgent / LangGraph 覆盖。
- 因此若开源，差异化只能押在"极简 + 单 GPU 进程内显存生命周期"，
  且必须论证优于「Ollama + Talos」这类组合。**当前设计文档完全没有这段陈述——这是开源最致命的缺口。**

## 五、开源岔路（未决）

| | 自用版（先接住自己的流程） | 开源版（给别人用） |
|---|---|---|
| 通用性 | 刚好够用，允许为自有场景取舍 | 不能绑业务假设，抽象要干净 |
| 文档 | 自己看懂即可 | README / 插件开发指南 / 架构说明 / 示例 |
| 工程化 | 能跑就行 | 单元测试 / CI / 版本号 / LICENSE / 变更日志 |
| API 稳定性 | 随时改 | 发布后要承诺兼容 |
| 工作量 | 1x | 2–3x，多出来的几乎全是非功能性工作 |

**建议**：先按自用版跑通 1–2 条真 workflow，再谈开源。
理由：① 未跑过真流程就开源 = 开半成品，别人一上手就撞上第二节的接缝问题；
② 开源会逼着"通用化"，反而破坏克制。

## 六、工程可复制性规范（用户明确要求）

因为未来可能上传 GitHub 或搬到其他主机，以下为硬性要求：

1. 所有源码与工程文件集中在 `ai_framework/` 单目录，自包含
2. 依赖登记在 `requirements.txt`，注明 Python 版本下限
3. 密钥只存 `.env`（已在 `.gitignore`），仓库里只有 `.env.example` 模板
4. 禁止硬编码绝对路径，统一 `pathlib` 相对项目根
5. `outputs/` `runs/` 等产物不入库
6. 设计与决策全部写入 `docs/`，不依赖对话上下文
7. 从第一天起用 git 记录历史（本地仓库已初始化，**并已推送远端**）
